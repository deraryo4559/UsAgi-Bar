# ウサギBar 要件定義書

最終更新: 2026-05-23
バージョン: 0.1（要件定義ドラフト）

---

## 1. アプリ概要

「ウサギBar」は、自宅にあるお酒・ドリンク・割材の在庫を、**酒棚のような見た目で楽しく管理する** Webアプリケーションです。

メイン画面は「酒棚そのもの」を表現し、登録済みのお酒・ドリンクが画像付きで並びます。アイテムをクリックすると詳細画面に遷移し、そのアイテムを使って **現在の在庫だけで作れるカクテル** を確認できます。

アプリのマスコットは **サングラスをかけた白いうさぎ**。ゆるく、少しふざけていて、宅飲み感のある親しみやすい「バーの案内役」というキャラクター設計です。

---

## 2. コンセプト

- **棚を眺める楽しさ**: スプレッドシート的な在庫管理ではなく「自分のバー」を眺める体験を最優先する
- **AIは補助役**: Gemini は写真からの情報抽出や表記ゆれ補助に使うが、判定や登録の主導権は人間（管理者）が握る
- **根拠ベースのレシピ**: カクテルはあらかじめ用意した「カクテルDB」を根拠とし、AIに架空レシピを作らせない
- **個人運用・無料運用前提**: 自分用・宅飲み用の小規模アプリ。スケールよりも運用コストゼロを優先する

---

## 3. ターゲットユーザー

| 種類 | 説明 | 想定人数 |
|---|---|---|
| 管理者（=自分） | 在庫を登録・更新し、カクテルを楽しむ人。書き込み可能 | 1名想定 |
| 閲覧ユーザー（任意） | 友人など、棚を眺めて楽しむだけのゲスト。書き込み不可 | 0〜数名 |

> 仮定: MVPでは「管理者1名のみ」を想定し、不特定多数の閲覧は考慮しない。閲覧ゲストは次フェーズ以降。

---

## 4. 解決したい課題

- 家にどんなお酒・割材があるか、棚や冷蔵庫の中で **把握しきれない**
- 在庫がある「のに」毎回同じカクテルしか作らない
- 「今ある材料で何が作れるか」を毎回ググるのが面倒
- せっかく揃えたコレクションを **眺めて楽しむ手段がない**
- スプレッドシート管理は無味乾燥で、続かない

---

## 5. 主な利用シーン

1. **宅飲み前のチェック**: 棚を眺めて、今日何を作るか決める
2. **買い物前の棚卸し**: 何が足りないかを確認してから酒屋に行く
3. **新しいお酒を買ってきたとき**: 写真を撮って棚に並べる
4. **来客に酒棚を見せる**: スマホ画面を友人に見せて選んでもらう（将来的に閲覧モードで）
5. **飲み終わって残量を更新する**: 「半分くらいになったな」と直感的に更新する

## 6. 機能要件

### 6.1 メイン画面（酒棚表示）

- 登録済みアイテムを「酒棚」のレイアウトで一覧表示する
- アイテム画像、名前（任意で残量バー）を表示する
- アイテムをタップすると詳細画面に遷移する
- **酒棚以外の余計な要素は表示しない**（タイトル等、最小限のみ）
- ログイン済みの管理者のみ、管理者画面への導線（例: ふわっと表示する小さなボタン）を表示する

### 6.2 お酒詳細画面

- 表示項目: お酒名 / 種類 / 度数 / 容量 / 残量 / 画像 / メモ
- このお酒を **必ず使うレシピ** のうち、現在の在庫で作れるカクテル一覧
- 「あと○○があれば作れる」表示（次フェーズ）

### 6.3 ドリンク詳細画面

- 表示項目: ドリンク名 / 種類 / 容量 / 残量 / 画像 / メモ
- このドリンクを **必ず使うレシピ** のうち、現在の在庫で作れるカクテル一覧

### 6.4 管理者画面

- 管理者ログイン後のみアクセス可
- 機能:
  - 登録済みアイテムの一覧と検索・並び替え
  - 新規登録（お酒 / ドリンク / 割材）
  - 編集・削除
  - 残量更新（スライダー or プリセット: 100% / 75% / 50% / 25% / 空 など）
  - 写真アップロード
  - Geminiによる情報抽出ボタン
  - カクテルレシピ照合の手動実行ボタン（自動実行と併用）

### 6.5 管理者ログイン画面

- メール+パスワード認証（Supabase Auth）
- パスワードリセット導線

### 6.6 認証・権限

- 未ログイン: メイン画面と詳細画面の **閲覧のみ可** （MVPでは限定公開 or 公開）
- ログイン管理者: すべての書き込み操作が可能
- 管理者かどうかは `profiles.role = 'admin'` で判定（または RLS で `auth.uid()` を見る）

### 6.7 在庫DB

- アイテム種別: `alcohol`（お酒）/ `drink`（ドリンク）/ `mixer`（割材）
- 画像URL（Supabase Storage の公開URL or 署名URL）
- 残量を ml または % で保持（仮: `remaining_ml` を保持）

### 6.8 カクテルDB

- 事前に投入したマスターデータ（管理者が編集可、ただし主に固定）
- 各レシピは複数の `ingredients` を持つ
- 各 `ingredient` は必須/任意、代替グループ（例: ジンとウォッカは交換可、など）を持つ

### 6.9 レシピ照合

- 在庫DB × カクテルDB を **通常のプログラム処理で照合** する（AI不使用）
- 結果ステータス: `makeable`（作れる） / `near`（あと1〜2個で作れる） / `not_makeable`（作れない）
- 材料名の表記ゆれは、まず正規化テーブル/辞書で対応。それでも曖昧なケースのみ Gemini に補助判定させる（次フェーズ）
- 結果は `recipe_matches` テーブルに保存し、画面表示は高速にする

### 6.10 Gemini連携

- 呼び出しは **Supabase Edge Functions 経由**（Geminiキーをフロントに置かない）
- 用途（後述「AI利用方針」を参照）
- 結果は **候補として返すだけ**、即DB保存はしない。管理者の確認を必ず挟む

## 8. ページ構成と役割

| # | ページ | URL案 | 役割 | 認証 |
|---|---|---|---|---|
| 1 | メイン画面（酒棚） | `/` | 酒棚を眺める入口。詳細への導線 | 不要 |
| 2 | お酒詳細 | `/items/:id` | お酒情報と作れるカクテル | 不要 |
| 3 | ドリンク詳細 | `/items/:id` | ドリンク情報と作れるカクテル（同URL、type で出し分け） | 不要 |
| 4 | 管理者ログイン | `/admin/login` | ログインフォーム | 不要 |
| 5 | 管理者ダッシュボード | `/admin` | アイテム一覧と各種操作の入口 | 必要 |
| 6 | アイテム新規登録 | `/admin/items/new` | 写真アップロード→Gemini解析→確認→保存 | 必要 |
| 7 | アイテム編集 | `/admin/items/:id/edit` | 既存アイテムの編集・残量更新 | 必要 |
| 8 | カクテル一覧（任意） | `/admin/recipes` | カクテルDBの確認・編集 | 必要 |

> 仮定: 詳細画面のURLは `/items/:id` で統一し、type によって表示テンプレートを切り替える。

## 9. 権限設計

| 操作 | 未ログイン | 管理者 |
|---|---|---|
| 酒棚閲覧 | 可 | 可 |
| 詳細閲覧 | 可 | 可 |
| 在庫追加・編集・削除 | 不可 | 可 |

## 11. AI利用方針

### 11.1 Gemini に任せること

- 写真から、**お酒名・ドリンク名・種類・容量・度数などの候補を抽出する**
- カクテル説明文の **言い回しを整える**（オプション）
- 材料名の表記ゆれ判定の **補助**（例: 「ジン」と「ドライジン」が同一視できそうかをスコア提示）
- 作れるカクテルを並べる際の **おすすめ順の提示**（次フェーズ）

### 11.2 Gemini に任せないこと

- 「在庫に材料が揃っているか」の **最終判定** → 通常のプログラム処理
- カクテルレシピの **生成**（架空レシピ防止）→ カクテルDBを根拠にする
- DBへの **直接書き込み** → 必ず管理者確認を挟む

### 11.3 安全策

- Geminiキーは Edge Function の Secret に置く（フロント禁止）
- Edge Function は **管理者のJWTを検証** してから Gemini を呼ぶ（料金枯渇対策）
- 画像サイズ・MIMEを Edge Function 側でバリデーション
- 1日あたりの呼び出し回数に **上限を設ける**（Edge Function 内でカウント、または Supabase の `rate_limits` 的なテーブルを用意）

## 12. 無料運用前提での注意点

| 観点 | リスク | 対策 |
|---|---|---|
| GitHub Pages | サーバー処理ができない | Supabase を組み合わせる |
| Supabase 無料枠 | DB 500MB、Storage 1GB、Edge Functions 月50万回 | 画像はリサイズ、画像URLは長期キャッシュ |
| Gemini API | 無料枠を超えると課金 | Edge Function 側で日次上限 + JWT検証 |
| 画像容量 | スマホ写真は1枚3〜5MB | アップロード時に WebP / 長辺1024px に圧縮 |
| 帯域 | GitHub Pages の月100GB | 画像は Supabase Storage を直接参照 |
| 個人情報 | 認証情報の流出 | RLS 必須、`.env` のコミット禁止 |
| ベンダロック | Supabase 依存 | DB は素直な Postgres スキーマに保ち移行可能にする |

**指摘**: 「完全無料で運用する」のは画像枚数が増えると難しい場合がある。100アイテムを超えて画像が大きいと Supabase Storage 無料枠（1GB）を圧迫する可能性あり。圧縮を前提に設計すること。

## 15. 主要処理フロー（要約）

1. **お酒/ドリンク登録（MVPは手入力）**
   - 管理者がフォーム入力 + 画像アップロード → Supabase Storage 保存 → `inventory_items` に保存 → `recipe_matches` を再計算
2. **お酒/ドリンク登録（次フェーズ: Gemini併用）**
   - 写真アップロード → Edge Function 経由で Gemini 呼び出し → 候補を返却 → 管理者が確認・修正 → 保存 → 照合
3. **レシピ照合**
   - 在庫変化のたびに `recipe_matches` を更新（Edge Function or クライアント側で実行）
4. **残量更新**
   - 詳細画面 or 管理画面でプリセット選択 → `remaining_ml` 更新 → 必要に応じて照合再計算

---

## 16. 仮定（前提として置いたこと）

- 管理者は1名のみ
- 閲覧は公開でも問題ない（家のお酒情報は機密ではない）
- 写真は管理者本人が撮ったもののみ（外部画像URL対応はしない）
- カクテルDBは別途用意できる（例: 既存OSSのカクテルレシピ集を取り込む or 手作業で初期投入）
- 残量管理は ml ベースでも % ベースでも、UIはざっくり4段階で十分
- 棚のレイアウトは「段×アイテム並び」程度で、3Dや凝った演出は不要

## 18. 実装前に確認すべき論点

1. **カクテルDBの調達方法**: 著作権上クリーンなレシピ集をどう用意するか。これが詰まると全体が止まる。
2. **Supabase か Firebase か**: 本要件では Supabase 第一候補だが、Edge Functions の利用感や無料枠の限界を実機で確認すべき。
3. **GitHub Pages のルーティング制約**: HashRouter で問題ないか（SEO は不要なので問題なしと想定）。
4. **画像圧縮の担当**: フロントで圧縮するか、Edge Function でも検証するか。両方が安全。
5. **照合計算の実行場所**: クライアント or Edge Function。レシピ件数次第で判断（数百件ならクライアントで十分）。
6. **アイコン/マスコット画像の用意**: 著作権クリーンな画像を誰がどう用意するか。AI生成画像のライセンスも要確認。
7. **PWA 化の有無**: スマホで使うなら PWA 化したい。MVP に入れるか次フェーズか。
8. **オフライン対応**: 棚を眺めるだけなら閲覧オフライン対応の価値あり。スコープに入れるか。

## 20. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| カクテルDBが用意できない | アプリの中核機能が動かない | 着手前に必ず確保。最小10件でも開始可能にする |
| Supabase 無料枠超過 | 突然動かなくなる | 圧縮・キャッシュ・上限通知 |
| Geminiキー漏洩 | 不正利用で課金 | Edge Function 経由のみ、JWT検証、回数制限 |
| 表記ゆれで照合できない | 「作れる」が出ない | aliases テーブルで地道に育てる |
| GitHub Pages のキャッシュ | デプロイが反映されない | ファイル名にハッシュ、`Cache-Control` 検討 |
| 写真のEXIF回転問題 | 画像が横倒し | 圧縮時にEXIFを正規化 |
