写真登録 → Gemini解析 → 候補確認 → DB保存 → レシピ照合 → 酒棚反映。MVPでは [2][3] をスキップ。
1. 管理者が画像選択 → 2. Storage 保存 → 3. Edge Func → Gemini
候補抽出 → 4. 候補返却
名前/種類/度数/容量
↓
5. 管理者が確認・修正 → 6. inventory_items に保存 → 7. recipe_matches 再計算 → 8. 酒棚に反映
MVP の場合: [1] → [5]手入力フォーム → [6] → [7] → [8] と直線的に進む。Gemini 連携は次フェーズで [2][3][4] を挿入する。

8. ドリンク / 割材 登録処理フロー

お酒とほぼ同じ。違いは「度数なし」と「ingredient_type が drink / mixer」。
1. 管理者が画像選択 → 2. Storage 保存 → 3. Edge Func → Gemini
名前/種類/容量を抽出 → 4. 候補返却
↓
5. 管理者が確認・修正
item_type を drink/mixer 選択 → 6. inventory_items に保存 → 7. recipe_matches 再計算 → 8. 酒棚に反映
お酒との差分は「alcohol_percentage を入れない」「サムネ色を分ける」「detail 画面のセクション名を出し分ける」のみ。

9. レシピ照合ロジック図

在庫DB × カクテルDB を、表記ゆれ辞書経由で正規化して比較する。判定は makeable / near / not_makeable の3値。
在庫DB
inventory_items
↔ 表記ゆれ辞書
ingredient_aliases
カクテルDB
cocktail_ingredients
↓ 正規化して名前マッチ
必須/任意 + 代替グループを考慮し
不足材料を集計
↓ 判定
作れる
必須材料すべて在庫あり
あと一歩 (near)
不足が1〜N個（次フェーズ）
作れない
不足多数
判定アルゴリズム概要（疑似コード）: 
for each recipe in cocktail_recipes:
  required = recipe.ingredients.filter(i => i.is_required)
  missing = []
  for each ing in required:
    inStock =
      inventory.find(item => normalize(item) == normalize(ing.name))
      || inventory.find(item => sameSubstituteGroup(item, ing))
    if not inStock:
      missing.push(ing.name)

  if missing.length == 0:    status = "makeable"
  elif missing.length <= 2: status = "near"        // 閾値は未決定 (U6)
  else:                      status = "not_makeable"

  recipe_matches.upsert({recipe_id, status, missing})
判定は 通常のプログラム処理（純TS or SQL） で行う。Gemini は「normalize() が確信を持てない曖昧ケース」のみ補助判定に使う（次フェーズ）。
